# Вариант 18 — граф зависимостей Alpine APK

Решение пяти этапов практической работы по конфигурационному управлению.
Программа самостоятельно читает `APKINDEX.tar.gz`, выбирает указанную версию
пакета и строит граф зависимостей алгоритмом BFS **без рекурсии**.
Для получения зависимостей не используются менеджеры пакетов или сторонние
библиотеки. Нужен **Python 3.11+**, установка зависимостей не требуется.

## Быстрый запуск

Linux/macOS/WSL:

```sh
chmod +x run.sh
./run.sh examples/acyclic.toml
make test
make check
```

Windows PowerShell:

```powershell
$env:PYTHONPATH = "src"
python -m apkgraph examples/acyclic.toml
python -m unittest discover -s tests -v
python scripts/check_style.py
```

Сборка не нужна: проект запускается из исходников. При желании проверить
компиляцию: `python3 -m compileall -q src`. Файлы кэша исключены в `.gitignore`.

## Настройки TOML

Все пять параметров анализа задаются только в TOML. Пример:

```toml
package = "A"
repository = "acyclic.json"
test_mode = true
version = "1.0-r0"
max_depth = 10
```

| Поле | Тип | Значение и проверка |
| --- | --- | --- |
| `package` | string | Имя APK; в тестовом режиме только буквы A–Z |
| `repository` | string | HTTP(S) URL каталога одной архитектуры или JSON-файл |
| `test_mode` | bool | `true` — JSON, `false` — настоящий APKINDEX |
| `version` | string | Точная APK-версия корня, включая ревизию `-rN` |
| `max_depth` | int | Неотрицательная глубина; корень имеет глубину 0 |

Все поля обязательны, неизвестные поля отвергаются. Логические значения не
принимаются вместо чисел. Путь JSON отсчитывается от каталога TOML-файла.
URL может заканчиваться на `APKINDEX.tar.gz`; иначе это имя добавляется.
Нужен каталог архитектуры, например `.../v3.22/main/x86_64`, а не сайт Alpine.

На границе глубины вершина сохраняется, но её зависимости не раскрываются.
Если корень отсутствует в индексе в **точно указанной** версии, программа
выводит ошибку. Индекс обычно содержит только актуальную версию ветки;
для старой версии нужен соответствующий архивный репозиторий.

## Демонстрация этапов

Параметр `--stage` выбирает этап демонстрации и не меняет настройки анализа.

```sh
./run.sh examples/acyclic.toml --stage 1  # пять строк ключ=значение
./run.sh examples/busybox.toml --stage 2 # прямые выражения зависимостей APK
./run.sh examples/acyclic.toml --stage 3 # список смежности после BFS
./run.sh examples/acyclic.toml --stage 4 # зависимости раньше потребителей
./run.sh examples/acyclic.toml --stage 5 # описание PlantUML
```

По умолчанию выбран этап 5. В режиме 2 выражения вроде
`so:libc.musl-x86_64.so.1` сохраняются в исходном виде из APKINDEX.
В графе виртуальная зависимость заменяется реальным пакетом-поставщиком.
Идентификатор вершины имеет вид `имя@версия`.

Пример этапа 4:

```text
D@1.0-r0 -> B@1.0-r0 -> C@1.0-r0 -> A@1.0-r0
```

Код завершения 0 означает успех, 2 — ошибку входных данных, сети или порядка
на циклическом графе. Диагностика идёт в stderr, результат — в stdout.
На цикле этапы 3 и 5 работают, этап 4 сообщает об отсутствии порядка.
При ограничении глубины этап 4 предупреждает об усечённом графе.

## Тестовый репозиторий

JSON-объект сопоставляет имя из A–Z версии и списку зависимостей:

```json
{
  "A": {"version": "1.0-r0", "dependencies": ["B"]},
  "B": {"version": "1.0-r0", "dependencies": []}
}
```

Можно задавать ограничения, например `B>=1.0`. Один тестовый файл содержит
одну версию каждого имени. Отсутствующая зависимость вызывает ошибку, если
она должна быть раскрыта в пределах `max_depth`.

Примеры: `acyclic.toml` — ромб, `cycle.toml` — цикл из трёх вершин,
`isolated.toml` — отдельный пакет, `depth1.toml` — усечение на глубине 1.

## Визуализация

По варианту требуется **вывести описание**, поэтому PlantUML печатается
на экран. Готовые описания для трёх реальных пакетов находятся в
`docs/comparison/`. SVG выдаются отдельно на странице скачивания;
сгенерированные изображения исключены из учебного git-репозитория.

```sh
./run.sh examples/busybox.toml > busybox.puml
# Необязательно: отрисовка внешним PlantUML (не входит в программу)
java -jar /path/to/plantuml.jar -tsvg busybox.puml
```

Стрелка идёт от пакета к зависимости. Изолированные вершины и циклы
сохраняются. Метки экранируются, вместо имён в рёбрах используются алиасы.

## Алгоритмы и пределы решения

BFS использует `deque`, отмечает вершину при постановке в очередь и хранит
минимальную глубину. Циклы не приводят к повторному раскрытию.
Порядок вычисляется алгоритмом Кана по обратным рёбрам, начиная с листьев.
Построение графа и сортировка имеют сложность O(V+E) без учёта разрешения
имён и выбора версий; индекс поставщиков строится один раз.

Поддерживаются прямые имена, виртуальные `provides`, ограничения `=`, `<`,
`<=`, `>`, `>=`, `~`, числовые компоненты версий, суффиксы APK и ревизии.
При нескольких кандидатах выбирается наибольшая версия пакета, при равенстве
— первое имя по алфавиту. Для виртуального имени с ограничением используется
версия из `provides`, а не версия пакета-поставщика.

Это анализатор метаданных одного репозитория и архитектуры. Он не решает
глобальную задачу совместимости установки: не выбирает совместный набор
версий с откатом, не обрабатывает `install_if`, теги репозиториев и состояние
установленной системы. Конфликты `!package` не являются рёбрами и выводятся
отдельно в stderr. При их наличии порядок графа не обещает успешную установку.
Индекс не проверяется по подписи; программа ничего не устанавливает.
Ограничение архива и APKINDEX — 64 MiB, сетевой тайм-аут — 30 секунд.

Эти отличия от полного решателя `apk` объясняют возможные расхождения на
сложных наборах пакетов. Для трёх приведённых примеров связи и порядок
совпали с штатными инструментами. Подробности и исходные результаты:
[отчёт](docs/report.md).

## Структура и функции

- `src/apkgraph/config.py` — строгая схема TOML.
- `repository.py` — загрузка APKINDEX, JSON и разрешение поставщиков.
- `versions.py` — сравнение версий и проверка ограничений.
- `graph.py` — BFS, порядок загрузки и определение усечения.
- `plantuml.py` — формирование диаграммы.
- `__main__.py` — CLI пяти этапов.
- `tests/` — 28 автономных тестов, включая HTTP-сервер на localhost.
- `scripts/check_style.py` — структура, история, файлы и правила Python
  из PDF, включая сложность, числа в сравнениях и имена.

Полный список функций и методов: [API](docs/api.md). Описание в начале
каждой функции оформлено как docstring. Инструкции по публикации и истории
пяти этапов и исправлений приведены в отчёте. Публичный репозиторий ещё не создан.

Результаты проверки правил: [аудит репозитория](docs/repository-audit.md).

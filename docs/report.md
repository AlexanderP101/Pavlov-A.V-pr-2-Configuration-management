# Отчёт по варианту 18

Дисциплина: «Конфигурационное управление», сборник практических работ № 2.
Группа по исходному заданию: ИКБО-12-25. Вариант 18, страницы 59–61.
Язык реализации: Python 3.11+. ФИО исполнителя не указано.

## Соответствие требованиям

| Этап | Реализация | Демонстрация |
| --- | --- | --- |
| 1 | CLI и пять обязательных полей TOML | `--stage 1`, тесты `test_config.py` |
| 2 | Прямое чтение APKINDEX, точная версия корня | `--stage 2`, `test_repository.py`, `test_remote.py` |
| 3 | BFS без рекурсии, минимальная глубина, циклы | `--stage 3`, ромб, цикл, петля, цепочка из 1501 пакета |
| 4 | Зависимости перед потребителями, цикл диагностируется | `--stage 4`, сравнение с `apk add --simulate` |
| 5 | Текст PlantUML в stdout | режим по умолчанию, три `.puml`; SVG выдаются отдельно |

Каждый этап сохранён отдельным Conventional Commit. История находится
в `.git` внутри передаваемого проекта. Архив для передачи не является
отслеживаемым файлом репозитория. APKINDEX и apk-tools скачивались в рабочий
каталог вне проекта; бинарный менеджер пакетов в проект не входит.

## Сценарии на тестовом репозитории

```sh
./run.sh examples/acyclic.toml --stage 3
./run.sh examples/acyclic.toml --stage 4
./run.sh examples/depth1.toml --stage 3
./run.sh examples/depth1.toml --stage 4
./run.sh examples/cycle.toml --stage 3
./run.sh examples/cycle.toml --stage 4
./run.sh examples/cycle.toml --stage 5
./run.sh examples/isolated.toml --stage 5
```

Ромб: A → B, A → C, B → D, C → D. BFS-порядок: A, B, C, D.
D имеет глубину 2 и появляется один раз; оба входящих ребра сохраняются.
Порядок загрузки: D, B, C, A. B и C независимы, их можно переставить.

Глубина 1: только A, B, C и два ребра из A. D не попадает в граф.
Порядок B, C, A корректен лишь для усечённого графа, о чём выводится
предупреждение. При глубине 0 остаётся только A.

Цикл: A → B → C → A. BFS завершается с тремя вершинами и тремя рёбрами.
PlantUML содержит все рёбра. Этап 4 возвращает код 2 с сообщением
«Цикл: порядок загрузки невозможен…»; частичный порядок не выдаётся за полный.

Изолированный пакет A: одна вершина, рёбер нет, порядок состоит из A.
В дополнительных автоматических тестах проверены петля A → A,
неразрешимая зависимость, конфликт, виртуальный поставщик и длинная цепочка.

## Демонстрация ошибок параметров

Исправить копию `examples/acyclic.toml` и выполнить `--stage 1`:

| Изменение | Результат |
| --- | --- |
| `package = ""` или `"abc"` при `test_mode=true` | Ошибка имени |
| `repository = "absent.json"` | Файл не найден |
| В реальном режиме `repository = "not-a-url"` | Ожидается HTTP(S) URL |
| `test_mode = 1` | Ожидается true или false |
| `version = "bad"` или `"1...."` | Неверная APK-версия |
| `max_depth = -1`, `true`, `1.5` | Ожидается целое число >= 0 |
| Удалить поле или добавить `typo = 1` | Ошибка строгой схемы |
| Повредить TOML | Ошибка синтаксиса |

Ошибки каждого поля проверяются тестами. Точная отсутствующая версия
обнаруживается на этапе чтения репозитория, а не подменяется другой.
HTTP 404, повреждённый gzip/tar и отсутствие APKINDEX также проверяются.

## Сравнение с Alpine APK

Дата проверки: 13 ноября 2026 года. Репозиторий:

```text
https://dl-cdn.alpinelinux.org/alpine/v3.22/main/x86_64
```

Использован настоящий `apk-tools-static` версии **2.14.13-r0** для x86_64.
Для сравнения взят один и тот же скачанный APKINDEX. `apk` запускался
с пустым изолированным корнем и локальным индексом. Установка не выполнялась:
команды установки и загрузки запускались с `--simulate`.
Менеджер пакетов использовался только для внешней проверки результатов,
не для получения данных внутри разработанного инструмента.

| Корень | Версия | Прямые выражения D | Разрешённые рёбра | Порядок |
| --- | --- | --- | --- | --- |
| busybox | 1.37.0-r20 | `so:libc.musl-x86_64.so.1` | busybox → musl | musl, busybox |
| zlib | 1.4-r0 | `so:libc.musl-x86_64.so.1` | zlib → musl | musl, zlib |
| musl | 1.2.5-r13 | нет | нет | musl |

Точные результаты: `comparison/*-order.txt`, `*-apk-add.txt`,
`*-apk-dot.txt`, `*-apk-fetch.txt`. Текст PlantUML — `*.puml`, изображения SVG выдаются отдельно на сайте скачивания. Образец записей выбранных трёх пакетов сохранён как
`comparison/APKINDEX.sample`. Контрольные суммы — `comparison/snapshot.txt`.

Для busybox и zlib набор рёбер совпадает с `apk dot`. Различаются синтаксис,
оформление и подписи: apk показывает конкретный атом `so:...` на ребре,
наш PlantUML показывает пакет-поставщик с версией без подписи атома.
Для musl у `apk dot musl` пустой граф и код 1: эта команда не выводит
изолированный пакет. В PlantUML корневая вершина сохранена явно.
Это различие визуализации, а не расхождение данных о зависимостях.

Порядок `musl → busybox`, `musl → zlib` и одиночный `musl` совпадает
с порядком действий в `apk add --simulate` в пустой базе.
`apk fetch --recursive --simulate --url` перечисляет сначала корневой пакет,
затем musl. Это порядок перечисления файлов для загрузки, а не порядок
удовлетворения зависимостей. В работе под «порядком загрузки зависимостей»
принят порядок, при котором каждый пакет идёт после своих зависимостей;
поэтому сравнение выполнено прежде всего с планом установки `apk add`.

Сравнение версий дополнительно проверено на **1521 паре** (39 × 39) против
`apk version -t`. Использованы обычные версии, ведущие нули, буквенные
компоненты, alpha/beta/pre/rc, git, p и ревизии. Расхождений не обнаружено.
Это проверка набора примеров, а не формальное доказательство для всех строк.

Для повторения сравнения с собственным исполняемым файлом apk:

```sh
# Сначала скачать APKINDEX.tar.gz той же ветки/архитектуры.
python3 scripts/compare_apk.py /path/to/apk.static /path/to/APKINDEX.tar.gz
```

Для свежего индекса версии могут измениться. Перед запуском сетевых примеров
нужно проверить их актуальность в APKINDEX и изменить `version` в TOML.
Инструмент намеренно не заменяет запрошенную версию последней.

## Проверки и ограничения

Выполнены `make test` (28 тестов), `make check`, запуск реального HTTP-источника,
сравнение с apk и отрисовка трёх диаграмм внешним PlantUML 1.2026.1.
Автономные тесты не требуют доступа в интернет; HTTP проверяется на localhost.

Основные отличия от полного менеджера пакетов описаны в README:
локальное разрешение без глобального отката, один репозиторий/архитектура,
без installed/world, install_if, проверки подписей и обработки конфликтов
как задачи решателя. Поэтому на сложных пакетах результат может отличаться
от полного плана установки. Усечённый граф также не является полным планом.

## История и публикация

```sh
git log --oneline --reverse
```

В архиве сохранены пять последовательных коммитов этапов
и дополнительный коммит с исправлением правил оформления. Публичная
публикация не выполнялась: адрес аккаунта и репозитория не задан.
После создания пустого репозитория выбранного git-сервиса:

```sh
git branch -M main
git remote add origin <URL-вашего-репозитория>
git push -u origin main
```

Не следует инициализировать новую историю поверх переданной: это потеряет
демонстрацию этапов. Для защиты нужно указать ФИО в отчёте и самостоятельно
объяснить BFS, обработку циклов, границу глубины и разрешение `provides`.
